## Supabase and data

- **Supabase query errors resolve, they do not reject** (`{data: null, error}`): `Promise.all` over failing queries completes normally with empty arrays.
- **An empty-but-successful query (`[]` is truthy) overwrites loaded arrays,** and RLS returns exactly that shape when the auth token is not yet applied. "Only overwrite when non-empty" is wrong (it freezes cross-device deletes). #74 and #75 are the same bug class: failed and empty collapsed into one path.
- **Warm-reload empty-query race:** `resolveWarmReloadRace(previousState, result, refetch)` trusts an empty result only if the previous state was empty, otherwise refetches once. It lives in `src/lib/warmReloadRace.ts` (unit-tested) and is applied to bills, expenses, funds, members, expense_splits, bill_splits, pay_schedules and pay_history (#348), plus the legacy `paydays` table (unused; the app's real pay data is `pay_schedules` / `pay_history`). `assumeEmptyPreviousState` is only for the household-switch call site (stale closure). `joinHousehold` cleanup uses it with a live refetch; an inconclusive (null) result skips the destructive cleanup and logs.
- **State-desync bug class** (#74, #89, #90, #96, #73, #82): reviewers check every new AppContext state for it. The notification-generation effect must be gated on `isOnboarded` (#90: a cross-user write of user B with household A on a same-tab account switch).
- **Deployed edge functions drift from the repo:** `join-household` sat at deployed version 1, so every join created a `household_members` row with a null user id and the user landed back on onboarding forever. After editing `supabase/functions`, run `supabase functions deploy` and check the deployed version through the MCP `list_edge_functions` / `get_edge_function`.
- **Delete-user FK cascades:** `household_members`, `notification_settings` and `notifications` had user FKs as NO ACTION; the `cascade_delete_user_fks` migration fixed it, so deleting a user from the Auth dashboard now works.
- `notifications.household_id` is NO ACTION and its RLS only allows deleting own rows, so a client-side household delete fails. Owner leave-household goes through the `delete-household` edge function (service role, re-derives ownership with `is_household_owner()`, clears notifications for all members, then deletes the household). Leaving (#251) also goes through an edge function, `leave-household` (service role): it recomputes the rules, can set another member's role, moves `households.user_id` (a creator record only since #350/ADR 0006, fixed against app users by a trigger) to a remaining accepted owner or nulls it, clears the leaver's notifications for the household, then deletes the leaver's member row by id. `households.user_id` may be null (#350); RLS trusts membership and role only. A triggers-only migration (`20261017120000_household_last_owner_guards`) stops app users deleting an owner's member row (skipped when the household row is already gone, so an owner deleting the household still cascades) and demoting the last accepted owner. Service-role deletes skip the triggers (`auth.uid()` is NULL), so two owners leaving at the same instant could leave zero owners; accepted. What leaves with the leaver: their pay schedule, pay history, bill splits, contribution rules, household contributions and expense splits cascade; goals (`funds.member_id`), bills and expenses (`assignee_id`) are SET NULL and stay unassigned. `delete-household` refuses while another accepted owner exists. Known gap: `joinHousehold` can still delete a user's old household client-side (conflicts with this ticket's intent; follow-up filed). Deploy order for this change: migration, then both functions (verify deployed versions), then merge.
- `bills_frequency_check` allows only lowercase `weekly` / `fortnightly` / `monthly` / `yearly`. Onboarding once sent capitalised values; `FrequencyToggle`, the bill edit sheet and the Add flow use lowercase.
- **`updateBill` / `updateExpense` used to delete and re-insert the split rows on every save** (and `updateBill` rewrote both dates), so renaming a shared bill wiped its shares and a rename on a rolled-forward autopay bill saved the screen's date over the stored one (R10, #397). Both now skip the split rows when `splitsData` is undefined, and `updateBill` writes a date only when the payload has that key. A one-field edit must pass only what it changes; rebuilding splits resets every row's status to Pending.
- **`bills.payment_type` is stored capitalised** (`Auto` / `Manual`); only the client `mapBillFromDb` lowercases it. The server cron path does not normalise, so always compare case-insensitively (this caused the false overdue pushes, #154).
- **This database holds other real households.** Always scope notification and bill queries by `household_id` or `user_id`, never a bare bill-name join (generic names like Rent collide).
- **Blast-radius rule before deleting test data:** confirm each household's member list is exactly the test accounts, and that no real users or `notifications` rows reference them. Delete households first (cascades to members, bills, funds, paydays), then the `auth.users` rows.
- Test accounts with throwaway addresses cannot receive confirmation emails: confirm them with a SQL `email_confirmed_at` update. Never record real test or user email addresses in docs (public repo).
- The real roster should be only Anthony's household plus whatever fresh test account he creates; clean strays with a blast-radius check.
- Do not add per-component `isDataLoading` guards: AppShell withholds all children while a session is loading, so they are dead code (SPEC A2).
- **Canary (SPEC A2):** the old Health score read an empty household as exactly 85, "Fully Funded". The verdict (R25) reads empty arrays as grey "Set up your pay", so an unexplained grey "Set up your pay" or "Add your bills" on a household that has data now means something passed empty arrays: look at the loading state, not the rule. Two mechanisms are known so far, #73 (empty collection overwrites) and #74 (failed and empty collapsed into one path).

## Notifications

- **#134 root cause was not timezone:** a legacy client "app is open" path in `AppContext.tsx` pushed immediately, ignoring `notify_hour`. The fix splits rows into push-now and deferred (`scheduled_for` set, `delivered_at` null). The deferred-row day calculation must use `todayInZone(householdTz)`, not the device-local `todayYmd`, which is wrong whenever household and device timezones differ.
- **#132:** the overdue dedupe key must roll daily (`...-overdue-${todayYmd}`), or an overdue bill notifies once ever. Manual bills previously generated zero overdue reminders (`diffDays < 0` was excluded); auto-pay bills exactly one.
- **#139:** `notification_settings.overdue_bill_reminders` (default true) is AND-gated with `manual_bill_reminders` / `auto_pay_reminders`. Due-soon and day-0 reminders are unaffected.
- **Snooze was removed entirely,** including a second localStorage-scanning copy in `AppShell.tsx` that drove the bell badge. Grep `snooze` repo-wide before touching notification UI.
- All dedupe keys are calendar-day or cycle-stable, never a call-time timestamp. A unique index backs the upsert; `ignoreDuplicates` compiles to `ON CONFLICT DO NOTHING`, so repeat generation runs are safe no-ops and leave `scheduled_for` untouched. The payday reminder key is parsed with `parsePaydayLogPayDate` in `generateReminders.ts` (no migration).
- The delivery job skips rows with `is_read` true; mark-read is the only way to stop a pending push (#209).
- The delivery job writes `delivered_at` per user inside the loop, not in one batch at the end, to avoid a double send if the `maxDuration=60` function times out.
- Rollover of recurring paid bills lives in the 15-minute reminders job, not the 5-minute delivery job, so "rolls within a few minutes" really means up to 15.
- Paused bills generate no reminders (#201); pausing marks the pauser's rows read at once and other members' within one cron run (up to 15 minutes).
- `public/sw.js` `notificationclick`: links with params always `client.navigate()` an open window (fallback `openWindow`); this also affects bill links.
- **"Late" pushes:** the payload had no send-time timestamp, so the OS stamped render time. `push.ts` now stamps `timestamp: Date.now()` and the service worker passes it through. Web push has no delivery-time guarantee; lateness is a device-queue artifact.
- A member who receives no pushes needs a `notification_settings` row (created lazily on first client load) and a `push_subscriptions` row (only when that person taps Enable push on her own device). A missing subscription is swallowed (marked delivered, nothing sent). Ask the member to check Settings before assuming a logic bug (#145).
- Reminder timing: a household's notify hour only matters relative to a fixed run; the 15-minute pg_cron generation job is what makes it meaningful (see `docs/environment.md`).

The bare `eslint` script also lints `supabase/functions` Deno code (about 13,900 problems versus about 100 with `eslint .`), so baselines differ by scope, not regression. Do not run a "fix lint" pass without reading this.

After an implementer reports a commit, verify its parent is the expected tip, bring it in with `git cherry-pick`, and clean up with `git worktree remove --force` plus `git branch -D`.

- Bumping `CACHE_NAME` in `public/sw.js` was the manual-test redeploy trigger pattern (PR #121). `prebuild` now stamps it per deploy, and a local build dirties `public/sw.js`: never commit that change.
- Two dead Stop/Notification hooks were once found in Anthony's global `settings.json`; cross-project hook errors may not come from this repo.
- Impeccable is a design tool that complements, not replaces, code review. Hold the first full-app critique until after Slice 13 is merged, and never start it unprompted.

## Process

- **Always delegate diff review to a separate sub-agent,** never the orchestrator (keeps its context small and respects separation of duties). Implementer and reviewer are always different agents. The fix loop returns to the same builder (full context) and a fresh reviewer, not the original finder or the builder, checks the fix. Reviews caught real bugs in #75, #101, #85, #106, #143 and #161, so never skip one.
- The independent reviewer re-runs tsc, lint and build and verifies claims against the live DB and code rather than trusting the builder's prose. Independent schema review queries live Supabase, not the migration file. Do not accept an agent's "no duplicate found" grep at face value: the same bug pattern had a third occurrence in a file already touched (#161); the reviewer re-greps.
- A sub-agent pushing back on a brief is a good sign; check specific line-number claims rather than accepting either agent's. A security-classifier flag on a sub-agent's tool use must be verified independently (read the full diff, re-run queries) before acting.
- **Self-approval of money-facing calculations is refused:** if Anthony says "just merge, you approve it", push back on separation of duties and confirm explicitly.
- **Verify production after a merge:** a green squash-merge is not proof. After any merge, especially one touching the `vercel.json` cron, confirm a production deployment reached READY through the Vercel MCP (`list_teams`, `list_projects`, `list_deployments` with target production, `get_deployment`). The Hobby cron incident (#96 half B) is why.
- **Session start:** run `gh pr list` for an unmerged docs PR carrying a newer HANDOFF (a stale HANDOFF caused an out-of-order build on 2026-09-27), and check local main against origin ahead/behind (three doc-only commits sat unpushed for two days). When a doc says work is done, check GitHub too (#99 was still open after HANDOFF said merged); run `gh issue list --state open`.
- **Parallel builds must use isolation worktrees** (a shared checkout collided); parallel read-only reviews are fine; with no worktree, build sequentially on one branch. Stacked PRs: retarget the base to main after the parent merges (`gh pr edit N --base main`) and recheck CI.
- (History, pre-2026-10-11 preview workflow.) Anthony often folds bugs found in manual testing into the same branch and PR (one merge cycle), and sometimes works live on a preview URL, so a follow-up goes on the same open PR branch rather than a new stacked PR.
- (History: since 2026-10-11 the default is `needs-merge-approval`; `needs-manual-test` only on request.) Labels: `needs-manual-test` only when platform or device behaviour is the thing fixed; `needs-merge-approval` for a review that found issues or genuine ambiguity; relabel when Anthony cannot exercise a feature (he does not use Direct Pay). `needs-info` means waiting on Anthony; `ready-for-human` means partial human execution (for example #156 domain and DNS steps).
- Investigate before building: "#98 sub-slice 6" turned out to be a no-op (expenses already shared categories). Present that to Anthony rather than build a no-op. A pure-schema slice still goes through normal review; it is not schema-only when UI and AppContext wiring ride along.
- Migration plus app code in one task: the sub-agent writes the migration file only; the orchestrator applies it via Supabase MCP after independent review and Anthony's schema sign-off, then verifies live counts. Account, domain or DNS setting changes are things the orchestrator does not do even with permission: post step-by-step instructions for Anthony.
- For small features the orchestrator runs the discovery interview itself (plain language, one question at a time, skipping the heavy crd skill) and then files the issue. A CRD is not needed for clear bug fixes.
- Code review uses the code-review skill (Standards and Spec axes) through a separate sub-agent.
- Keep stale line references out of docs and comments; SPEC citations drifted before (#92 re-verified 11 and fixed 2).

## Known non-blocking items

- **Rules targeting a Just tracking goal (R17, #404, known interim):** a Just tracking goal is excluded from the Goals totals, health score, Dashboard goal cards, surplus suggestions, new-rule goal pickers and milestone reminders, but a contribution rule that already points at one still fires in `checkAndApplyRules` (so money still lands on the goal) and still counts in the Bills Household total. The pace line ignores percentage rules and variable pay and so will not match the Household total, which ignores pay thresholds.
- **Hannah's bill-reminder pushes (#145)** are parked, unresolved, and no build should be scoped until Anthony talks to her. Theory: `sendPushToSubscriptions` in `src/lib/push.ts` only cleans up on an exact 404/410; other failures are silently `console.error`ed.
- **Expenses are implicitly weekly** (no frequency column). This was inferred from a sub-slice-1 migration comment and a live production magnitude cross-check; the source `bills.frequency` was never SQL-verified. Percentage-of-surplus rules are excluded (their payout depends on an unknowable future surplus; same "don't estimate the unknowable" precedent as #106). A rule amount is converted from the triggering member's own pay-schedule frequency, falling back to monthly when there is zero or more than one schedule (a builder default, unconfirmed).
- **Bills and expenses share one interleaved list** (grouped by category, amount descending). Anthony rejected separate tabs ("I hate the switch"), and a bills/expenses filter request reopens that decision. #157 (the bills filter cannot isolate expenses) is logged out-of-spec in `CHANGE-LOG.md` with a cheap third dropdown if he wants it. Manual past-dated one-off bills never get a label so they still count (small drift from `money.md`; legacy rows only). The filtered-expenses list and the hidden-note flag duplicate one predicate.

New households take the timezone of the creating phone (#249); the Australia/Sydney fallback stays for when it can't be read and for existing rows. The `join-household` edge function also checks server-side; that check fails open if its own query errors, and a race surfaces a raw Postgres error.
