# Lessons and known items

One line each (or close). These were learned the hard way; do not relitigate them. No line numbers: they go stale within a session, so re-grep after editing.

## Testing

- **Claude sessions must not create Funded users or type passwords:** login hits the live Supabase. Anthony does the manual testing; a session may seed `TEST-` rows into his household by SQL in the exact state needed and delete them after. Local Supabase (Docker) with a seeded test user was offered as the only compliant route for Claude to log in; Anthony declined for now.
- **Seeding OVERDUE test bills pushes a real "Bill Overdue" to Hannah household-wide.** Seed just before testing, warn Anthony first, and delete before NZ midnight (a new day is a new overdue dedupe key, so another push).
- **Push taps are only testable after merge:** the 5-minute delivery job calls production, so the link is built by live code. Inbox-only items are testable on the PR preview.
- **Push test method:** insert a `notifications` row for Anthony with `scheduled_for = now()` and `delivered_at = null`; the push arrives within about 5 minutes (once per subscription, so several). For inbox-only set `delivered_at = now()`. To re-show an old item set `is_read = false` (the inbox hides read items). Tag the `dedupe_key` `TEST-...` and delete after. A push can also be driven through the app's own push-send route with a page-scoped fetch that never returns the session token.
- **Payday test rows need the real dedupe_key shape** `<scheduleId>-<YYYY-MM-DD>-payday_log_pay` (not `TEST-`), or the link falls back to plain `/payday`. Use the real schedule id and pay date, and delete after.
- Test "no push" cases (for example Undo) by checking DB rows, not by waiting for a push.
- Fully close and reopen the installed app first, so the new service worker is active before live checks.
- **User-switch and auth-state cases must be tested in a single tab without reloading;** a fresh load hides the bug. A cold-start-only checklist would have passed that regression.
- **Code review is not a substitute for a device pass:** Slice 7 was caught by Anthony on his phone.
- Verify features end to end against a disposable test household with hand-computed expected numbers, not just by reading code. State plainly what was verified by code read only (failure paths, Direct Pay gating) rather than claiming a live pass.
- Test in the machine's real timezone (the dev box is Pacific/Auckland, UTC+12, which reproduces positive-offset date bugs) and also empirically with `TZ=America/New_York` for negative offsets.
- Preview has no Production-only env vars; routes must fail with a clear "not configured" message there. The bug-report token is Production-only, so the bug-report path cannot be watched end to end on a preview.
- **pr-browser-triage** runs against the local `npm run dev` (launch config in `.claude/launch.json`) using disposable test accounts, never the owner's real accounts. Worked example, PR #77: classify each checklist item Full / Partial / Not-testable and get an approval gate before executing; it came out 8 Full, 7 Partial, 0 Not-testable. Partial means sub-second flash timing, offline or throttled network (no offline control in the browser tool), and PWA process-kill semantics. A hard reload of a signed-in tab is a real reload in Chromium, so "no flash" checks need a screen recording.
- Firing browser-automation calls too fast after a page transition can produce phantom failures (onboarding seeming to skip a step, an empty "Fully Funded" shape). Re-run one action at a time before calling it a product bug.
- The browser tool auto-suppresses native `confirm()` / `alert()` (returns false); set `window.confirm = () => true` through JS exec before the click. Its screenshot compositor may be unavailable; prove absence with `read_page` or DOM inspection, which is more precise than a screenshot anyway.
- **Test data accumulates** in the production Supabase project (households, bills, notifications, auth users from test runs). Before deleting a test household or account, verify its member list is exactly the test accounts and that no real user or `notifications` row references it (see Supabase and data). Re-verify by querying: earlier "cleanup done" log claims were wrong.
- **iOS installed-app storage is a separate container from Safari data.** Safari "Clear Website Data" does not reach it; only delete and reinstall forces a cold state. So offline cold-load recovery (#71) was never device-verified (merged anyway by Anthony).
- Manual tests run in chronological batches: each failure round goes through a fresh independent reviewer before it returns to Anthony's phone.
- **Samsung Internet draft-loss (#168)** was merged without Hannah's device test. Reopen it if she reports the draft lost after attaching a screenshot. The draft persists to sessionStorage with a 2-minute expiry, cleans up on unmount, carries a `hadScreenshot` flag and a `submittedRef` guard; React 19 only wires `onCancel` on a dialog, so use a native cancel listener.
- Owed live checks on Hannah's Android: #182 (payday taps, 30 Sep reminder) and #193 (goal push tap). Any failure reopens the issue.

## Supabase and data

- **Supabase query errors resolve, they do not reject** (`{data: null, error}`): `Promise.all` over failing queries completes normally with empty arrays.
- **An empty-but-successful query (`[]` is truthy) overwrites loaded arrays,** and RLS returns exactly that shape when the auth token is not yet applied. "Only overwrite when non-empty" is wrong (it freezes cross-device deletes). #74 and #75 are the same bug class: failed and empty collapsed into one path.
- **Warm-reload empty-query race:** `resolveWarmReloadRace(previousState, result, refetch)` trusts an empty result only if the previous state was empty, otherwise refetches once. It is applied to bills, funds, paydays, members and bill_splits. `assumeEmptyPreviousState` is only for the household-switch call site (stale closure). `joinHousehold` cleanup uses it with a live refetch; an inconclusive (null) result skips the destructive cleanup and logs.
- **State-desync bug class** (#74, #89, #90, #96, #73, #82): reviewers check every new AppContext state for it. The notification-generation effect must be gated on `isOnboarded` (#90: a cross-user write of user B with household A on a same-tab account switch).
- **Deployed edge functions drift from the repo:** `join-household` sat at deployed version 1, so every join created a `household_members` row with a null user id and the user landed back on onboarding forever. After editing `supabase/functions`, run `supabase functions deploy` and check the deployed version through the MCP `list_edge_functions` / `get_edge_function`.
- **Delete-user FK cascades:** `household_members`, `notification_settings` and `notifications` had user FKs as NO ACTION; the `cascade_delete_user_fks` migration fixed it, so deleting a user from the Auth dashboard now works.
- `notifications.household_id` is NO ACTION and its RLS only allows deleting own rows, so a client-side household delete fails. Owner leave-household goes through the `delete-household` edge function (service role, re-derives ownership with `is_household_owner()`, clears notifications for all members, then deletes the household). A non-owner leave deletes their own member row scoped by both user id and household id.
- `bills_frequency_check` allows only lowercase `weekly` / `fortnightly` / `monthly` / `yearly`. Onboarding once sent capitalised values; `FrequencyToggle` and `AddBillSheet` use lowercase.
- **`bills.payment_type` is stored capitalised** (`Auto` / `Manual`); only the client `mapBillFromDb` lowercases it. The server cron path does not normalise, so always compare case-insensitively (this caused the false overdue pushes, #154).
- **This database holds other real households.** Always scope notification and bill queries by `household_id` or `user_id`, never a bare bill-name join (generic names like Rent collide).
- **Blast-radius rule before deleting test data:** confirm each household's member list is exactly the test accounts, and that no real users or `notifications` rows reference them. Delete households first (cascades to members, bills, funds, paydays), then the `auth.users` rows.
- Test accounts with throwaway addresses cannot receive confirmation emails: confirm them with a SQL `email_confirmed_at` update. Never record real test or user email addresses in docs (public repo).
- The real roster should be only Anthony's household plus whatever fresh test account he creates; clean strays with a blast-radius check.
- Do not add per-component `isDataLoading` guards: AppShell withholds all children while a session is loading, so they are dead code (SPEC A2).
- **Canary (SPEC A2):** the empty state scores exactly 85 (100*0.4 + 50*0.3 + 100*0.3), which clears the 80 "Fully Funded" threshold. An unexplained "Fully Funded" on the dashboard means something passed empty arrays: look at the loading state, not the formula. Two mechanisms are known so far, #73 (empty collection overwrites) and #74 (failed and empty collapsed into one path). The empty household shows "Not Set Up Yet" as a display-layer override in the health card; the score function is untouched.

## Notifications

- **#134 root cause was not timezone:** a legacy client "app is open" path in `AppContext.tsx` pushed immediately, ignoring `notify_hour`. The fix splits rows into push-now and deferred (`scheduled_for` set, `delivered_at` null). The deferred-row day calculation must use `todayInZone(householdTz)`, not the device-local `todayYmd`, which is wrong whenever household and device timezones differ.
- **#132:** the overdue dedupe key must roll daily (`...-overdue-${todayYmd}`), or an overdue bill notifies once ever. Manual bills previously generated zero overdue reminders (`diffDays < 0` was excluded); auto-pay bills exactly one.
- **#139:** `notification_settings.overdue_bill_reminders` (default true) is AND-gated with `manual_bill_reminders` / `auto_pay_reminders`. Due-soon and day-0 reminders are unaffected.
- **Snooze was removed entirely,** including a second localStorage-scanning copy in `AppShell.tsx` that drove the bell badge. Grep `snooze` repo-wide before touching notification UI.
- All dedupe keys are calendar-day or cycle-stable, never a call-time timestamp. A unique index backs the upsert; `ignoreDuplicates` compiles to `ON CONFLICT DO NOTHING`, so repeat generation runs are safe no-ops and leave `scheduled_for` untouched. The payday reminder key is parsed with `parsePaydayLogPayDate` in `generateReminders.ts` (no migration).
- The delivery job writes `delivered_at` per user inside the loop, not in one batch at the end, to avoid a double send if the `maxDuration=60` function times out.
- Rollover of recurring paid bills lives in the 15-minute reminders job, not the 5-minute delivery job, so "rolls within a few minutes" really means up to 15.
- `public/sw.js` `notificationclick`: links with params always `client.navigate()` an open window (fallback `openWindow`); this also affects bill links.
- **"Late" pushes:** the payload had no send-time timestamp, so the OS stamped render time. `push.ts` now stamps `timestamp: Date.now()` and the service worker passes it through. Web push has no delivery-time guarantee; lateness is a device-queue artifact.
- A member who receives no pushes needs a `notification_settings` row (created lazily on first client load) and a `push_subscriptions` row (only when that person taps Enable push on her own device). A missing subscription is swallowed (marked delivered, nothing sent). Ask the member to check Settings before assuming a logic bug (#145).
- Reminder timing: a household's notify hour only matters relative to a fixed run; the 15-minute pg_cron generation job is what makes it meaningful (see `docs/environment.md`).

## Tooling and machine

- **Vercel Hobby allows cron once per day only.** An hourly `vercel.json` cron silently never promotes to production (the site keeps serving the last good build). Use pg_cron + pg_net + Vault for anything finer than daily; reach for it before any Vercel cron change (`docs/adr/0004-pg-cron-for-scheduling-not-vercel-cron.md`).
- **The auto-mode classifier blocks `apply_migration`** (twice on a data-fix migration, even with an `autoMode.allow` entry), an Agent spawn that tells a sub-agent to apply a migration, `gh pr merge` ("Merge Without Review"), adding permission rules ("Self-Modification"), and reading a session token out of localStorage (credential extraction). Do not retry and do not edit `settings.json`: hand Anthony the SQL-editor steps or the command (he merges by hand or adds `Bash(gh pr merge:*)` himself). A sub-agent writes the migration file; the orchestrator applies it after sign-off.
- **Gemini CLI is dead** (IneligibleTierError; the free Code Assist tier was discontinued). Never use the `gemini-cli` MCP and do not re-diagnose it. Offloading goes through agy.
- **agy:** call as `& .\scripts\agy-delegate.ps1 ... -Files @('a','b')` from PowerShell; it only reads files passed with `-Files` inside the repo. It refuses `.sql` and `.claude/` paths (exit 4), `.env*`, `.git` and PNGs, so paste schema facts into the prompt and stage worktree diffs as a temp `.md` in the repo root (delete after). `-Task plan` was removed: planning always goes to a Claude sub-agent. A blocked tool retries once; a second failure exits 3 and falls back to a Claude sub-agent. Its line-level claims can be incomplete (it missed 2 of 16 grep hits), so verify. The kit's `UPDATE-PROMPT.md` was not refreshed; re-sync keeps `scripts/agy-delegate.ps1` byte-identical and keeps this repo's adapted rules 5 and 6.
- **agy kit re-sync rule:** future kit updates get re-synced here; the script must stay byte-identical (see `docs/environment.md` for the kit location and the #183 loose end).
- `npm run lint` fails outright on the repo (pre-existing errors, including the `loadData` trigger effect, which is a hard byte-identical constraint). The bare `eslint` script also lints `supabase/functions` Deno code (about 13,900 problems versus about 100 with `eslint .`), so baselines differ by scope, not regression. Do not run a "fix lint" pass without reading this.
- Use Write plus `--body-file` for GitHub issue and PR bodies; heredocs and PowerShell here-strings break on long markdown, and `git commit -m` with an inline here-string containing double quotes fails. `gh api -f field=@path` silently posts the literal string on this Windows setup: use `-F`, and read back any `gh api` PATCH or POST that embeds file content.
- Sync local main after a squash-merge with `git fetch` plus `git reset --hard origin/main`, not `git pull` (a plain pull creates a spurious merge bubble). A branch held by a worktree needs `git worktree remove --force` then `git branch -D`. Use `gh pr merge --squash --delete-branch`.
- `isolation: "worktree"` sub-agents can land on a stale base or be unable to check out a branch checked out elsewhere. After an implementer reports a commit, verify its parent is the expected tip, bring it in with `git cherry-pick`, and clean up with `git worktree remove --force` plus `git branch -D`.
- A 529 Overloaded killed implementation runs: prefer a fresh agent with a tight self-contained brief and exact anchors over resuming a long transcript.
- Bumping `CACHE_NAME` in `public/sw.js` was the manual-test redeploy trigger pattern (PR #121). `prebuild` now stamps it per deploy, and a local build dirties `public/sw.js`: never commit that change.
- Two dead Stop/Notification hooks were once found in Anthony's global `settings.json`; cross-project hook errors may not come from this repo.
- Impeccable is a design tool that complements, not replaces, code review. Hold the first full-app critique until after Slice 13 is merged, and never start it unprompted.
- tailwindcss-animate was never installed, so `animate-in` / `fade-in` / `zoom-in` were no-ops in 10 files (including Dialog) until Slice 13 installed it.

## Process

- **Always delegate diff review to a separate sub-agent,** never the orchestrator (keeps its context small and respects separation of duties). Implementer and reviewer are always different agents. The fix loop returns to the same builder (full context) and a fresh reviewer, not the original finder or the builder, checks the fix. Reviews caught real bugs in #75, #101, #85, #106, #143 and #161, so never skip one.
- The independent reviewer re-runs tsc, lint and build and verifies claims against the live DB and code rather than trusting the builder's prose. Independent schema review queries live Supabase, not the migration file. Do not accept an agent's "no duplicate found" grep at face value: the same bug pattern had a third occurrence in a file already touched (#161); the reviewer re-greps.
- A sub-agent pushing back on a brief is a good sign; check specific line-number claims rather than accepting either agent's. A security-classifier flag on a sub-agent's tool use must be verified independently (read the full diff, re-run queries) before acting.
- **Self-approval of money-facing calculations is refused:** if Anthony says "just merge, you approve it", push back on separation of duties and confirm explicitly.
- **Verify production after a merge:** a green squash-merge is not proof. After any merge, especially one touching the `vercel.json` cron, confirm a production deployment reached READY through the Vercel MCP (`list_teams`, `list_projects`, `list_deployments` with target production, `get_deployment`). The Hobby cron incident (#96 half B) is why.
- **Session start:** run `gh pr list` for an unmerged docs PR carrying a newer HANDOFF (a stale HANDOFF caused an out-of-order build on 2026-09-27), and check local main against origin ahead/behind (three doc-only commits sat unpushed for two days). When a doc says work is done, check GitHub too (#99 was still open after HANDOFF said merged); run `gh issue list --state open`.
- **Parallel builds must use isolation worktrees** (a shared checkout collided); parallel read-only reviews are fine; with no worktree, build sequentially on one branch. Stacked PRs: retarget the base to main after the parent merges (`gh pr edit N --base main`) and recheck CI.
- Anthony often folds bugs found in manual testing into the same branch and PR (one merge cycle), and sometimes works live on a preview URL, so a follow-up goes on the same open PR branch rather than a new stacked PR.
- Labels: `needs-manual-test` only when platform or device behaviour is the thing fixed; `needs-merge-approval` for a review that found issues or genuine ambiguity; relabel when Anthony cannot exercise a feature (he does not use Direct Pay). `needs-info` means waiting on Anthony; `ready-for-human` means partial human execution (for example #156 domain and DNS steps).
- Investigate before building: "#98 sub-slice 6" turned out to be a no-op (expenses already shared categories). Present that to Anthony rather than build a no-op. A pure-schema slice still goes through normal review; it is not schema-only when UI and AppContext wiring ride along.
- Migration plus app code in one task: the sub-agent writes the migration file only; the orchestrator applies it via Supabase MCP after independent review and Anthony's schema sign-off, then verifies live counts. Account, domain or DNS setting changes are things the orchestrator does not do even with permission: post step-by-step instructions for Anthony.
- For small features the orchestrator runs the discovery interview itself (plain language, one question at a time, skipping the heavy crd skill) and then files the issue. A CRD is not needed for clear bug fixes.
- Code review uses the code-review skill (Standards and Spec axes) through a separate sub-agent.
- Keep stale line references out of docs and comments; SPEC citations drifted before (#92 re-verified 11 and fixed 2).

Percentage-of-surplus rules are excluded (their payout depends on an unknowable future surplus; same "don't estimate the unknowable" precedent as #106).
