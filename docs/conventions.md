# Conventions

Binding build and process rules. Vocabulary lives in `docs/context/`; this file is about how to build and ship.

## Document roles

- `SPEC.md`: requirements, technical guardrails (Part A: A1 escalation gates, A2 standing rules) and the vertical slices. The working reference during builds. There is no separate CRD or design-reference document.
- New features: file a to-spec issue, agree it with Anthony, then fold it into `SPEC.md`.
- `CHANGE-LOG.md`: append-only inbox for out-of-spec requests, triaged on demand.
- `HANDOFF.md`: current state only (where we left off, what is next). Durable facts go to their home in `CLAUDE.md`'s "Where knowledge lives", never into `HANDOFF.md`. There is no archive file; git history holds prior versions.
- `docs/context/` holds vocabulary, `docs/adr/` holds hard-to-reverse decisions, `docs/lessons.md` and `docs/environment.md` hold lessons and operations.

## Versioning

- `src/lib/version.ts` (`APP_VERSION`) is the single source of truth for the display version. The `version` field in `package.json` is unused npm metadata and is not the source.
- Bump `+0.0.1` per build (`v0.9.x` while pre-testing; `v0.9.0` was deliberately skipped). Do not bump as a side effect of an unrelated change. A rework commit on the same open PR does not re-bump; a new build cycle does.
- Confirm the exact resulting version with Anthony immediately before merging to `main`. He can waive a bump. When parallel PRs collide on the version, renumber and confirm again.
- Milestones: `v0.10.0` when the app is ready for wider testers, `v1.0.0` for public beta. This is a loose guideline; the version applied at each merge is decided with Anthony at merge time.
- The version shows at the bottom of Settings and on the Updates card, both read from `APP_VERSION`; never restate the current version in a doc.
- **Long-lived redesign branch (#377) exception:** `redesign/full-app` carries no per-slice bump or patch note. One bump to `v0.10.0` and one patch-notes entry (written from the closed slices' "What's changing") happen in the final slice before the single merge. Testing exception too: Anthony checks each slice on the branch's Vercel preview (live `main` keeps the old app until the end), and each slice's commit range gets an independent sub-agent review. Migrations on that branch must be compatible with the old code still live on `main`, because preview and production share one Supabase.
- Merge conflicts on `version.ts` and `src/lib/patch-notes.ts` are common when two same-day PRs both bump: keep the higher version and both entries. If both land on the same version number, combine the bullets under one entry.

## Patch notes

Every version bump gets a patch-notes entry (the user-facing Updates file, `src/lib/patch-notes.ts`, hand-written, newest first) as part of the same PR, not a follow-up. This applies even to backend-only, infra, or under-the-hood changes with no UI difference: write what changed in plain language a non-technical user would understand, framing it around the practical effect (what is more reliable, what behaves differently, what to expect), not the mechanism. A pure internal change with genuinely zero user-facing effect still gets a one-line entry saying so (for example "cleaned up something behind the scenes, no visible change") rather than being skipped silently.

The Updates card (a compact non-blocking card above the bottom nav, #260) shows once per version, tracked by a last-seen version key in localStorage; write the key in the same pass that shows the card. It is delayed about 1200ms so it does not cover the first taps, shows the first 2 bullets of the newest entry plus "+N more", so put the most important changes in the first two bullets. The page is called Updates (#311). The hidden `/patch-notes` page is reached from Settings. The page shows only entries from the newest entry's month (measured from the newest entry, not today; `recentPatchNotes` in `src/lib/patchNotesWindow.ts` filters at render). Older entries stay in `patch-notes.ts`, never deleted; an entry whose `date` does not parse as "Month YYYY" is always shown. The card is unaffected. Docs-only or tooling-only PRs carry no version bump and no patch note.

## Getting started guide

- The public `/getting-started` page (copy in `src/lib/getting-started.ts`) is linked from Settings and from the Hazardous Schematics website. Never rename or move the URL.
- Every PR that changes user-visible behaviour states "Getting started guide: checked, no change" in its description, or includes the guide update. The independent reviewer checks that line. Docs-only and tooling-only PRs are exempt.
- Each "Good to know" item records the ticket it works around (data only, never shown). Delete the item in the PR that closes that ticket.

## README upkeep

- Every PR that changes project structure, screens, setup, env vars or key logic either updates `README.md` or states "README: checked, no change" in its description. The independent reviewer checks that line.
- Docs-only and tooling-only PRs are exempt unless they change something README describes.
- README never restates the current version (see the versioning rules above).

## Build conventions

- **TypeScript:** strict types, no `any` unless suppressed with a comment. One component per file, `PascalCase` filenames.
- **State** is centralised in `AppContext.tsx`; pages consume it through `useApp()` and `useCurrentUser()`. Every new piece of AppContext state must be checked for the state-desync bug class (see `docs/lessons.md`).
- **Styling:** Tailwind utility classes that reference the CSS custom property tokens; avoid hard-coded colour values. Check contrast in both themes (a lime Undo button on grey was near-invisible in light theme at 1.79:1).
- **Type and radii (R01, #388):** Instrument Sans for everything including numbers (tabular figures set on `body`; no monospace). Syne only on page-header `h1`s. Weights stop at 700 (`font-bold`); never `font-extrabold` outside Syne. Radii tokens: `--radius-card` 16px, `--radius-sheet` 28px, `--radius-input` 12px, pills and circles `rounded-full`; inner radius = outer radius minus the padding between them. `src/lib/designTokens.test.mjs` guards the banned classes, motion tokens and where `font-heading` may appear.
- **Motion is premium-minimal, no bounce.** Motion tokens (R01, #388): `--duration-quick` 150ms (press, toggles, chevrons), `--duration-feedback` 300ms (pop-ups, colour changes, menus), `--duration-structural` 550ms (expand/collapse); `--ease-enter` `cubic-bezier(.22,.31,0,1)` and `--ease-exit` `cubic-bezier(.69,0,0,1)`. The global default transition uses quick + enter. `.press` (scale .97 on `:active`) and `.press-tint` are the press utilities; a fill that should react to touch uses `:active`, never `:hover`. Collapse and expand use the `grid-template-rows` 1fr to 0fr technique with the shared tokens. `--ease-enter` is a decelerate curve that finishes opacity in the first 20 to 30%, so a crossfade on it looks like a pop: use ease-in-out for plain fades, and if a fade looks instant, check the easing token first. Keep the transition class always present and do instant dismissal through a `transitionDuration` DOM override, because toggling the class and the opacity in one render leaves nothing to transition from. Menus use an open / closing / closed state machine so the exit animation plays before unmount. Use the `useReducedMotion` hook for reduced motion.
- **Core controls (R02, #389):** use the `components/ui/` primitives, never hand-roll: `Button` (primary / ghost / destructive; content-sized, `fullWidth` only for the main action of a form; `buttonClasses()` for a Link that must look like one), `IconCircle` / `BackCircle` / `CloseCircle`, `Chip` (selected = 2px inset lime ring + bold label, no fill; keep at least 8px between chips because their 44px tap areas overlap otherwise), `Card` (tappable cards tint via `press-tint`, never scale), `Input` / `Select` / `Textarea`. Lime fills appear on `:active` only. Never combine `press` with a `transition-*` class (it overrides the press transition). `cn` knows the radius tokens, so `rounded-card` and `rounded-full` resolve against each other. The destructive label is black in dark and white in light (contrast). `src/lib/coreControls.test.mjs` holds the checks and the `rounded-[2px]` ratchet: delete a file from its allowlist when a slice restyles it; R35 empties it. `Dialog` has left the allowlist (28px `rounded-sheet`, R05).
- **Pop-up shells (R05, #392):** every pop-up uses `ui/Dialog` (28px `rounded-sheet`, portalled, `modal-backdrop`). Pick the shape by field count: `SingleCard` (1-2 fields, one main pill), `DetailSheet` (rows in a scrolling body, one pinned footer: `primary` full width, `secondary` pills and the red Delete equal width in one row, Delete last, behind a `ConfirmDialog`; F03, #466), `ConfirmDialog` (small, centred, red destructive), `StepFlow` (see "Step flow" below). `Field` is the label, control, helper and error block. Never `window.confirm`: the ratchet in `src/lib/sheetShells.test.mjs` lists the files that still call it; delete an entry when a slice moves that file to `ConfirmDialog`. Saves go through `useSheetSave` ("Saving…" with back and close locked; a failure keeps the pop-up open with a red line above the pill and "Try again"; success closes and toasts). A failure is a save that returns `false` or throws, so a mutation that swallows its error and only toasts must be changed to return `false` or throw. Bottom sheets (`placement="bottom"`) float with a gap and pin their pill about 8px above the keyboard via `--keyboard-inset`. Old pop-ups stay centred until their slice moves them into a shell. `Row` takes `tall` for 44px tappable rows in pop-ups.
- **Step flow (R06, #393):** use `ui/StepFlow` for creating anything with 4+ fields. Essential cards go in `steps`, optional ones in `extras` (reached only from summary rows via `edit(key)`); leave conditional steps out of `steps` and the flow clamps if one disappears. One `Field question` per card with `enterKeyHint="next"`; choice cards use `ChoiceField`, notes use `NotesToggle` on the summary. Pass `dirty` from `hasChanges` so closing after typing asks "Discard this {noun}?". Summary rows must be `type="button"`. Logic lives in `src/lib/stepFlow.ts`, guarded by `stepFlow.test.mjs` and `stepFlowShell.test.mjs`.
- **App shell (R03, #390):** every page uses `PageHeader` (`onAdd` + `addLabel` for the "+" circle, `onBack` for drill-downs, `showAvatar={false}` on Settings and Updates), never a hand-rolled header button. Anything docked above the bottom nav uses `var(--nav-clearance)`, never a literal offset. Nav slots live in `src/lib/navSlots.ts`. `src/lib/appShell.test.mjs` and `navSlots.test.mjs` guard it.
- **Carousel (R04, #391):** use `components/ui/Carousel` for any sideways set of cards, never a hand-rolled scroller. Native scroll-snap; auto-rotate is opt-in (`autoRotate`), restarts after each touch, and has a pause button that is first in tab order; the track is keyboard-reachable. Under Reduce Motion it still turns but swaps instantly. Dots jump to a slide. Logic in `src/lib/carousel.ts`; `carousel.test.mjs` and `carouselLogic.test.mjs` guard it.
- **Bills and expenses share one row vocabulary:** `RowPill` variants are primary (lime, Auto-Pay), success (green, Manual) and accent (amber, Expense).
- **Add flow (R07, #394):** `components/AddFlow` is the only way to add a bill or expense (Bills "+", `/bills?add=1`); payload and split rules live in `src/lib/addFlow.ts`. After a successful add a page calls `useRowHighlight().flash(rowKey(kind, id))` and puts `row-highlight` on an inner wrapper (never on an element that already animates; the wrapper id is `bill-<id>` / `expense-<id>`). Editing is the detail sheets (see "Detail sheets" below). Guarded by `addFlow.test.mjs` and `addFlowShell.test.mjs`.
- **Detail sheets (R10, #397):** `BillDetailSheet` and `ExpenseDetailSheet` are `ui/DetailSheet` (each renders its own status line as a child, one `Row tall chevron` per field; footer actions go through `primary` / `secondary` props, never in the body; the bill sheet shows ONE paid action via `billPaidAction`: Mark as paid, Mark as unpaid or Undo payment; every date row uses the same `en-NZ` short format, e.g. 13 Nov 2026); there is no Edit button or edit form. Each row opens `components/ItemFieldCard`: one `Field` in one `SingleCard` with a Save pill and a "Bill updated" / "Expense updated" toast, the draft seeded from the live item when the card opens and kept for "Try again". Open the card with `flushSync` and focus its box in the same tap, or iOS will not raise the keyboard. Parents pass the live item (look it up by id, as the Dashboard does with `bills.find`) so the sheet follows every save and closes itself if the item is deleted. Payloads and checks live in `src/lib/addFlow.ts` (`billUpdate`, `expenseUpdate`, `billFieldError`, `valuesFromBill`); the **split pass-through rule**: `updateBill` / `updateExpense` leave the split rows alone when `splitsData` is undefined, and `billUpdate` sends rows only for Split (always) and for Amount or Assigned to when the bill already had rows; `updateBill` writes `due_date` and `invoice_date` only when the payload carries those keys. `DetailSheet` takes `busy` (locks close, Escape, backdrop and Delete; the sheet also locks itself while its Delete question or a field card is open, so stacked Escape never closes the layer under a running save) and `actionError`. The four bill actions (`markAsPaid`, `markAsUnpaid`, `undoPayment`, `togglePauseBill`) resolve `Promise<boolean>` (true saved, false not) and a real failure shows a red line instead of a toast. Guarded by `itemEdit.test.mjs` and `detailSheets.test.mjs`.
- **Detail sheets II (R11, #398):** `GoalDetailSheet`, `PayScheduleDetailSheet` and the new `RuleDetailSheet` follow the R10 pattern (`ui/DetailSheet`, one `Row tall chevron` per field, a one-field `SingleCard` per row: `GoalFieldCard`, `PayFieldCard`, `RuleFieldCard`; `flushSync` + focus in the same tap; parents pass the live item by id: `funds.find`, `paySchedules.find`, and the rule sheet looks `contributionRules` up itself). `EditGoalSheet`, `AddPayScheduleSheet`, `RuleCard` and the dead `EditFundSheet`/`FundDetailSheet` are deleted; the goal sheet owns "Add amount" (`AddAmountModal` is now a `SingleCard` that calls `addToGoal` itself and shows a red line plus "Try again" on failure, #435) and "Rules for this goal" (a "+" opens `AddRuleFlow goalId=...`; each rule opens `RuleDetailSheet`). **Every goal save sends the whole goal** (`updateGoal` writes every column): `goalUpdate(values, goal)` keeps `member_id` and works the status out again (Saving: not started / in progress / reached; Just tracking = `paused`, saved amount kept). `addToGoal` and `deleteRule` now throw (`deleteRule` checks `.select()` like `deleteGoal`); rule allocation catches the throw itself, the Payday surplus allocation alerts it. Deleting a goal also deletes its rules, best effort. Only an owner with 2+ accepted members can change "Whose pay" on a pay schedule or rule (`canPickMember` in `lib/addPayFlow.ts`, app-side only). The Settings "Automation rules" list is now rows opening `RuleDetailSheet` (interim until R29). Guarded by `goalPayRuleEdit.test.mjs` (runtime) and `goalPayRuleSheets.test.mjs` (source).
- **Payday cards (R21, #408):** `lib/paydayCards.ts` (import-free, runtime-tested) decides the cards (every accepted member, plus anyone with pay; pay first by soonest date), the ring (days since last pay over cycle length: 7, 14, 30) and the wording. `MemberPayCard` sits in `ui/Carousel` (auto-rotate, peek when 2+); the card body is one button and the schedule tabs sit outside it. `MemberPaySheet` is a `DetailSheet` that renders its own contribution `SingleCard`, `AddRuleFlow` and `RuleDetailSheet`; the page renders the pay schedule sheet and `AddPayFlow`, stacked over it (the member sheet is `busy` meanwhile). `AddPayFlow` and `AddRuleFlow` take an optional `memberId` (skips "Whose pay"; only an owner with 2+ members can name someone else). `AddPayFlow.onAdded` now also gets the member id (the page highlights that member's card). The Payday files left the native-`confirm()` ratchet; `ContributionSettingsSheet` left the square-corner ratchet. Guarded by `paydayCards.test.mjs` and `paydayCardsShell.test.mjs`.
- **Restyle-only pop-ups (R13, #400):** the older pop-ups now sit on the shells with no behaviour change. Notifications (Chip tabs, Row-look inbox rows with an `IconCircle` trash and a tap body that is a button only when it has a destination, tall settings Rows with a local Switch), Push status (`SingleCard`, or a bottom `Dialog` with Done when no action is needed; closes after enabling, no toast), Avatar crop and upload, Join household, Email verified, Updates card, Edit and Remove member, and Settings (Delete household, Switch payment mode). Rules: a toast only when the sheet closes back to the page, never while another sheet stays open underneath (it would sit under the sheet's z-index); `ConfirmDialog` labels stay short (Delete, Switch, Remove); `SingleCard` takes `showThrownMessage` like `ConfirmDialog`; `useSheetSave` goes above any early return. Ratchets: the native-`confirm()` allowlist in `sheetShells.test.mjs` now holds only the Payday files, and the square-corner allowlist in `coreControls.test.mjs` shrank to login, onboarding, Contribution settings, Enter pay amount, Finish setup and Surplus suggestion.
- **Add goal flow (R08, #395):** `components/AddGoalFlow` is the only way to add a goal (Goals "+", `/funds?add=1`); rules live in `src/lib/addGoalFlow.ts` (import-free, so its `parseAmount` is a small copy of the one in `addFlow.ts`). Asks Kind (Saving or Just tracking), Name, Target, and for Saving an optional Already saved; Deadline and Category are summary extras. Just tracking saves with status `paused` (no schema change); Saving saves `not_started`, `in_progress` or `completed` from the amount saved. `addFund` returns the new id; `updateGoal` throws on failure and the goal sheet's field card shows the error. The Goals page uses `useRowHighlight().flash(goalRowKey(id), 600)` (the delay waits out the category expand). Notes are not asked (the `funds` table has no notes column). `AddGoalSheet` is deleted. Guarded by `addGoalFlow.test.mjs` and `addGoalFlowShell.test.mjs`.
- **Dates:** never use `toISOString().split("T")[0]` on a local-midnight date (it rolls back a day for UTC-plus households); use `toLocalYmd(date)`. `parseDateForDb` returns a date-only string unchanged. Server and cron code must pass the household-local today (`todayInZone(tz)` from `src/lib/notifications/timezone.ts`) into `displayedDueDate(bill, todayYmd)` (`src/lib/billCycle.ts`), never the Vercel process UTC clock; the cron and the UI must share that auto-pay rollforward so "overdue" agrees in both.
- **File pickers on iOS Safari:** a hidden input clicked from a script is unreliable inside sheets; use a label-wrapped input.
- **Safari and backdrop-filter:** Safari does not animate opacity on an element that also carries `backdrop-filter`; put the dim and blur on an inner element.
- **Dashboard tips** live in `dashboard-tips.ts` (plain string array). Update the tips whenever a shipped feature changes user-facing behaviour. The tips show one at a time in the Dashboard tip strip (R26).
- **Icons (#174):** the tab favicon and the home-screen icon (apple-touch-icon and manifest icons) are the light icon with a `?v=3` cache-bust; leave the manifest `theme_color`, `background_color` and the viewport `themeColor` alone. Trade-offs are in `docs/lessons.md`.
- **Live-check notes (replaces the manual-test checklist, 2026-10-11):** Anthony checks changes in production after merge, not on previews, unless he asks for a preview review (`needs-manual-test`, which then carries the checklist format in CLAUDE.md). Merge advice carries 1-3 plain-language lines on what to glance at (iPhone only); no checklist on the issue. Every issue has a "What's changing" section in plain terms.
- **Live-check notes target iPhone (iOS Safari) only,** never Android. Code must still work on iOS and Android.

## Standing constraints

- **Funded is a mobile app.** It is an installed home-screen app (iPhone for Anthony; Hannah uses Android in real life). Never lead with, test or ask about desktop behaviour.
- **Never commit directly to `main`;** work on milestone branches only. Issue closure triggers merge.
- The hard technical invariants (RLS mandatory, service-role key server-only, stack changes, the standing rules) live in `SPEC.md` Part A1 and A2. They are binding and are not copied here.
- **Goals, not Funds:** the `/funds` route is the Goals page. Say Goals in anything Anthony reads; the route and code names are unchanged and there is no app-wide rename.
